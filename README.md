# rig-c exam

An open-book exam for AI agents: build a rig from one painting with the published rig-c tools, and
write down what you expected before each step.

The tools are written for agents that cannot see what they build. This repository measures whether that
holds for an agent that has never seen the tools: the only help is what ships in the packages. Where an
examinee says *WTF?* — where what it expected and what happened differ — a document or a message is
missing something, and that line of the journal is what the exam is for.

## What this exam proves

That an agent with no memory of this project, given only the public packages and their documents, can read
the tools' refusals and produce a rig or a motion that passes the gate: that the toolchain's messages and
documents are enough of an interface. Rigs of this kind are used in two forms, and each edition tests one.
**Form 1, the living illustration**, is this edition, Basic: one painting becomes parts that breathe, blink
and let their hair and cloth answer physics, with gestures that stay inside what was painted, and seams that
never open. **Form 2, the motion-designed rig**, is the Advanced edition ([`advanced/`](advanced/)): a mannequin or a
stylised character with cut joints and alternates, motion retargeted onto it, feet planted.

## Rules

1. **Open book, closed neighbours.** You may read anything inside the two pinned packages once installed
   (`README.md`, `docs/`, `--help`, the examples they ship) and anything on their public repository pages.
   From the next sitting after the 2026-10-25 ruling, you may also read this clone's `grade.py` source:
   the exam measures whether the packages and their documents suffice, and `TASK.md` states the bars.
   Historical source reads and their recorded dispositions are preserved; this permission does not
   retrospectively void or rewrite any sitting.
   Other rig-c repositories are not in the book: rig-c/getting-started walks task 01's own painting, and
   rig-c/examples holds trials on it. The grade notes, without changing a line, any animation handed in
   with the shape the guide's scripts write (`from_the_guide` in `result.json`).
   You may not read another examinee's run, and you may not ask a person. Every run is public, under
   `results/`, because the results are. The clone the prompt makes leaves that directory out — not checked
   out and not downloaded — so nothing an examinee greps or lists can turn an answer up by accident;
   reading one takes a deliberate step, and a run by an examinee that took it measures nothing, and its
   journal usually shows it.
2. **Pinned versions.** `package.json` at the root names the round's versions. `npm ci` installs them;
   use those and no others.
3. **Journal before you act.** Keep the journal with `tools/journal.py`, in the form `JOURNAL.md` gives.
   Before every step (a build, a render, a measurement, a grader run), `open` writes the entry's first
   three lines (what you read, what you expect, what you chose and what you turned down); `run` runs the
   step; after you have read its output, `close` writes what happened, quoting it. An entry written after
   the fact is worth nothing here; a wrong expectation written beforehand is the most useful line in the
   file. The tool keeps a hash chain beside the journal (`.journal/`), and `grade.py` prints whether it is
   intact: a journal whose chain is broken, or that the tool did not write, is not kept, and the task is
   disqualified. The chain catches an entry edited, deleted or reordered after the tool wrote it; it does
   not stop a deliberate forgery of the chain itself, and it cannot show that an expectation was real.
4. **Submit the transcript.** `tools/journal.py` writes `transcript.md` beside the journal: each step's
   command, its start and end, its exit code and the last lines of its output. The raw record of your
   session, the export your agent can give, remains the proctor's cross-check: the two are compared.
   **Ruling, 2026-10-25:** a grader run outside an entry is an omission to record; it does not alone
   disqualify an intact tool-written chain. A grader before `start` or after `finish` also leaves an
   incomplete task clock. Preserve the literal clock and record the event; do not repair the hand-in.
   The chain cannot reveal an unrecorded command. The [proctor checklist](PROCTOR.md) cross-checks
   actual host command records and states when evidence is unavailable or partial.
5. **Say what the tools were missing.** At the end, `tools.md` lists what you wished the two packages had
   told you or let you do: what you were trying, what you had, what would have helped. It is read for the
   tools, not graded.
6. **The grader rebuilds.** Only your inputs are trusted: `grade.py` builds from the files the task says
   you hand in, on the pinned versions. Outputs you paste are not read.
7. **Stopping is an answer.** If you cannot go on, write the last entry — what you tried, the message
   you could not act on — and submit. A run that stops honestly is graded as stopped, not discarded.

## Layout

    tasks/<task>/TASK.md        the problem, what you are given, what you hand in, the pass lines
    tasks/<task>/inputs/        task-local painting and layers, when supplied (input roots below)
    fixtures/mannequin/         task 05's supplied config, inputs/ and caps/
    PROMPT.md                   the prompt every examinee is given, verbatim
    JOURNAL.md                  the journal's form
    tools/journal.py            the journal's only writer: python3 tools/journal.py --help
    grade.py                    the grader: python3 grade.py runs/<your run>
    runs/                       where you write: runs/<date>-<model>-<task>/ — empty here
    runs/<run>/config.json      your hand-in config; <run> ends with its task name
    runs/<run>/*.json           a separate motion file, if the config names one
    results/                    every run that has been read, filed by the model that did the work:
                                results/<model>/<date>-<name>/<task>/ holds the files handed in, the
                                proctor's regrade (result.json), its reading (READING.md) and pictures;
                                who.json beside them says who did the work and what the run counts as.
                                results/void/ holds runs that are kept and not counted.
    results.py                  writes this page's sitting summary and the full table in results/README.md
    advanced/                   the Advanced edition: motion from a pose sequence on a built rig, in three
                                rounds, with its own prompt, results and tables — see advanced/README.md

### Manual build from clone root

`runs/<run>/` is the hand-in directory. It does not change the package CLI's working directory or asset
base. In a manual `rig-parts build`, relative `--config`, `--source`, `--full`, `--head` and `--out` paths
are read from the shell's working directory. Paths **inside** the config, including limb `cap` images
and `motion.animations_from`, resolve from the directory containing that config.

For task 05, this example copies the supplied idle rig into a **new** run directory and builds it from
the clone root, after `npm ci` and with Bun on PATH. Choose an unused run name. The subshell stops if
`mkdir` fails, so pasting it again cannot overwrite an existing run's config.

```sh
(
  set -e
  run=runs/example-05-dance
  mkdir "$run"
  cp fixtures/mannequin/config.json "$run/config.json"
  cp -R fixtures/mannequin/caps "$run/caps"
  ./node_modules/.bin/rig-parts build \
    --config "$run/config.json" \
    --source fixtures/mannequin/inputs/painting.png \
    --full fixtures/mannequin/inputs/layers/full \
    --head fixtures/mannequin/inputs/layers/head \
    --out "$run/out"
)
```

The copied config still names `caps/*.png`, so those images must be beside it as `runs/example-05-dance/caps/`
for this manual build. Changing cwd does not supply a missing config-relative cap. If you separate your
authored motion into `dance.json`, put it beside the config and set `motion.animations_from` to `"dance.json"`.
Keep the supplied fixture unchanged; edit your run's config. The command above builds the supplied idle,
not a completed dance. `out/` is generated output, not a hand-in input.

The grader prepares a different layout: it copies the run's **top-level `.json` files** except `result.json`
and `usage.json` beside an isolated working config and links in the fixture's inputs. It also stages named
fixture assets, such as caps: `grade.py`'s `named_paths` recursively examines strings in both the supplied
fixture config and the run config, normalizes relative paths, and selects those that exist under the fixture
directory, excluding `.` and paths starting with `..`. Absolute paths are excluded from that selection.
Existing destinations and paths under `inputs` are skipped when copying. This is the grader's staging
selection, not a package path refusal rule. A manual package build does not perform this staging.
**The local `caps/` copy is for manual builds; it is not an additional required hand-in.** Follow the task's
hand-in list, including its separate motion file when used.

For tasks without a fixture, the grader uses that task's `inputs/` if it contains `painting.png`, otherwise
task 01's inputs. On the current tasks, the explicit manual input roots are:

| task | `--source` | `--full` | `--head` |
| --- | --- | --- | --- |
| 01, 02, 04 | `tasks/01-build/inputs/painting.png` | `tasks/01-build/inputs/layers/full` | `tasks/01-build/inputs/layers/head` |
| 03 | `tasks/03-correct/inputs/painting.png` | `tasks/03-correct/inputs/layers/full` | `tasks/03-correct/inputs/layers/head` |
| 05 | `fixtures/mannequin/inputs/painting.png` | `fixtures/mannequin/inputs/layers/full` | `fixtures/mannequin/inputs/layers/head` |

Supply the chosen task's run config and output paths explicitly too. Task 03 has its own painting; task
02 and task 04 currently use task 01's. The fixture's [folder guide](fixtures/mannequin/README.md#what-is-in-the-folder)
also gives the build command for a shell already inside `fixtures/mannequin/`.

## Sitting it

[`PROMPT.md`](PROMPT.md) is the prompt every examinee is given, verbatim — paste it into a coding agent
(one that can run commands and read and write files) with the model's name filled in by you, not by the
model. One model, one fresh session, one fresh clone. The proctor checks each run for two traces of a
prior look at an answer — an expectation, written before a build, that already knows what the build will
say; and hand-chosen numbers that match another run's — and says what it found in the run's reading.
Use the [proctor checklist](PROCTOR.md) for the pre-first-call context check and the command coverage
cross-check. An intact journal and the availability of host evidence are separate findings.

## Submitting

Make `runs/<YYYY-MM-DD>-<model>-<task>/` for each task you sat (`<task>` is the task's directory name, for
example `runs/2026-10-13-somemodel-01-build/`), commit only those directories on a branch of your fork,
and open a pull request against `main`.

Anyone may sit it with any model, in any coding agent. The pull request's form asks which model, which
agent, and whether a person stepped in; a run with help is still worth having, labelled as one. A workflow
regrades the run on the pull request and prints its lines in the job's summary.

`python3 grade.py runs/<run>` writes `result.json`; you may run it as often as you like — it is the same
grader, and what you learn from it belongs in the journal like any other step. The proctor regrades every
run from the files it hands in, looks at the pictures, establishes which model did the work, and files
the run under `results/` with a `READING.md`: what the journal caught, checked against the packages, and
which of it was filed on the tools. A run's own `result.json` is not trusted, and neither is its report.
