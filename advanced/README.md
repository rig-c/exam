# rig-c exam — Advanced

The second edition of the exam, and a different question. The Basic exam (the [repository's front
page](../README.md)) asks whether an agent can build a rig from one painting with the published tools. This one
starts from a rig that is already built and asks whether an agent can **put recorded motion on it** with
`@rig-c/pose` — a walk, a run, a dance, each taken from a person filmed face-on — and then **find and fix
what is wrong with the result**, when the only feedback is numbers. The examinee never sees the footage:
it gets the joints, cleaned, and a stick figure drawn from them.

The tools are written for agents that cannot see what they make. A retarget that "looks fine" is not
something an agent can report; a foot that slides 0.02 leg lengths a frame is. So every row of every table
here is a number the grader reads from the files the run hands in, and nothing that would need a person's
eye is a row.

This page is edition **0.21**. The fifteen sittings of 2026-10-18 below were graded on **0.20**, which is the
same edition less one row (shin scale, below); that row is shown beside them as a what-if, and the 0.20 verdicts
stand. The first nine of them sat 0.20 before three text fixes and one prompt sentence that moved no bar —
[the proctor's report](results/REPORT.md) says which. The three sittings of 2026-10-20 sat 0.21 itself, and
their shin-scale row is the one they were graded on.

## The three rounds

Each round is a directory that is a whole package: what the examinee is given and nothing else.

| round | the motion | what it adds | the problem and its table |
| --- | --- | --- | --- |
| [`R1`](R1/) | a walk: one stride cycle, repeated | feet that stay planted, lift as far as the person's, and do not slide | [R1/PROBLEM.md](R1/PROBLEM.md) |
| [`R2`](R2/) | a run: one cycle, repeated | an airborne span every stride, the pelvis sinking on landing and springing back, the pelvis tilting | [R2/PROBLEM.md](R2/PROBLEM.md) |
| [`R3`](R3/) | a dance: thirteen seconds that do not loop | holds, side steps, raised hands, three jumps, and a camera track that has to be written out beside the motion | [R3/PROBLEM.md](R3/PROBLEM.md) |

In each: `PROBLEM.md` (the situation, the tools, the pass table, the rules, what to hand in and what to
answer), `JOURNAL.md` (the journal's form), `PROMPT.md` (the same prompt as [the one here](PROMPT.md)),
`package.json` (the pinned versions), `tools/grade.py` (the grader) and `inputs/` (the rig, the pose
sequence, the stick figure).

The rig is the same character in all three, built as a 2D rig cut at its elbows and knees, with hair and
a skirt on physics. Its legs are 2D and face-on, so a knee that comes toward the camera has to be drawn
as a shorter leg — which is where the rounds differ most, and where the one row 0.21 adds comes from.

## The tables are fixed

Each `PROBLEM.md` carries its pass table under *Pass table (fixed before any sitting)*: every row a
measure, every bar a number, and how the grader reads it. They were written before the first sitting and
are not moved to fit a result. R2's table is R1's rows followed by the run's own; R3 drops the loop row,
because a dance does not loop.

**0.21 adds one row to all three**, *Shin scale*: the 5th percentile of the shins' rendered x-scale, over
every frame and both shins, is at least 0.4 of their setup length. On 0.20 a run could pass every row with
a lifted leg drawn at a tenth of its length — the rows that read the feet are satisfied by a foot that is
in the right place, however short the leg above it. The bar comes from the fifteen sittings themselves: thirteen
read 0.5 or more, and the two that did not read 0.106.

## Rules

1. **Open book, closed neighbours.** The examinee may read anything in the three packages the round
   installs (`rig-c`, `@rig-c/pose`, `@rig-c/parts`: their `README.md`, `docs/`, `--help`) and their public
   pages, and nothing else on the machine — not another sitting, not another copy of the exam, not this
   repository. It may not ask a person.
2. **Pinned versions.** The round's `package.json` names them: `rig-c` 2.59.0, `@rig-c/pose` 0.31.1,
   `@rig-c/parts` 1.35.0. `npm install` installs them.
3. **One round, one fresh session, one fresh copy of the package.** A session that has seen a round, or
   anyone's answer to one, does not sit another.
4. **Journal before you act.** Lines 1–3 of an entry before the step, line 4 after, `WTF?:` where the
   result was not what was expected. A journal written after the fact disqualifies the sitting. The rule
   entered the prompt after the first nine sittings below, because one of them said it had done so; that
   sitting is recorded, not voided.
5. **A clock and a transcript.** `run/transcript.md` opens with a `started:` line and closes with a
   `finished:` line, each the output of `date -u` at that moment.
6. **Say what the tools were missing.** `run/tools.md`, in the form `PROMPT.md` gives. It is read for the
   tools, not graded.
7. **The grader reads only what is handed in.** `tools/grade.py` reads the files the run hands in; a pasted
   result is not read, and a run's own grading is not the verdict.
8. **Stopping is an answer.** A run that writes its last entry and stops is graded as it stands.

## Sitting it

The person starting the sitting prepares the package; the model is started inside it and sees nothing else.

    git clone --filter=blob:none --sparse https://github.com/rig-c/exam.git exam
    cd exam && git sparse-checkout set --no-cone '/advanced/R1/'
    cp -R advanced/R1 ../advanced-R1-<model> && cd ../advanced-R1-<model>

(`R2`, `R3` the same.) Start a coding agent — one that can run commands and read and write files — in that
directory, in a fresh session, and paste [`PROMPT.md`](PROMPT.md) below its rule, with `<MODEL>` and `<ROUND>`
filled in by you. Then leave it: nobody answers during a sitting. The model replies at the end with five
answers and the grader's lines.

`PROBLEM.md` says R2 is sat after R1 and R3 after both. That order is not enforced: each round is graded on
its own, and the sittings below did not keep it.

## Submitting

Copy the round's `run/` to `advanced/runs/<YYYY-MM-DD>-<model>-<round>/` on a branch of your fork (`<round>`
is `R1`, `R2` or `R3`), add only that directory, and open a pull request against `main` saying which model,
which agent, and whether a person stepped in. No workflow regrades an Advanced run yet: the proctor runs
`tools/grade.py` on the files handed in, on the pinned versions, and files the sitting under `results/` with
its `result.txt` and a `who.json` — the model as you named it, the agent it ran in, the clock from the
transcript, and anything noted against it.

## Layout

    PROMPT.md                   the prompt every examinee is given, verbatim, once per round
    R1/ R2/ R3/                 the three packages, each exactly what the examinee is given
    results/                    every sitting that has been read:
                                results/<model>/<date>-<round>/ holds the files handed in (journal.md,
                                transcript.md, tools.md, report.md, findings.md, after/report.json, the
                                last build's output, after/camera.json for R3), result.txt (the proctor's
                                regrade, the verdict of record) and who.json. Render geometry is left out
                                (9.0 to 10.4 MB a sitting); so are the pictures and the clips.
    results.py                  writes the tables on this page and in results/README.md from results/

The date in a sitting's directory is the UTC day of its own `started:` line. The files are as handed in,
except that absolute paths on the machine the round was sat on are rewritten relative to the package.
