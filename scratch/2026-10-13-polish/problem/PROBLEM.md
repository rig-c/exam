# 문제: 춤추는 리그 손질하기 (1회차)

**무엇보다 먼저:** 이 세션이 이 문제나 그 풀이, 혹은 누군가의 풀이 보고(하위 에이전트의 것 포함)를 이미 본 적이 있으면 멈추고 그렇다고 말한다. 한 번의 응시는 모델 하나, 새 세션 하나다. 답을 본 세션에서 다시 풀면 당신이 아니라 그 답을 재게 된다.

## 상황

캐릭터 한 명(흰색 · 파란 줄 트랙 재킷, 검은 플리츠 치마, 운동화)을 2D 리그로 만들었고, 실제 댄서의 춤 영상에서 뽑은 관절 좌표로 그 리그에 춤을 입혔다. 큰 틀은 맞지만 영상과 나란히 보면 어색한 곳이 많다. 당신이 할 일은 **영상과 리그를 비교해서 무엇이 틀렸는지 찾고, 고칠 수 있는 것을 고치는 것**이다.

리그의 구조는 이렇다.

- 팔다리는 관절(팔꿈치 · 무릎)에서 잘린 단단한 조각이고, 관절에서 회전만 한다. 그래서 크게 꺾이는 동작은 회전으로 표현하지 않는다. 그 자세로 따로 그린 **교체 그림 세트**로 바꿔 끼운다. 세트는 K0~K4, 다섯 개다.
  - K0: 등 뒤로 깍지
  - K1: 머리 뒤에서 손 모으기
  - K2: 손을 아래로 모으기
  - K3: V사인 + 허리에 손
  - K4: 한 손 들기
- 세트는 팔 조각 + 몸통(재킷) 그림이 한 묶음이고, 같은 뼈에 붙어 있다. 그려진 각도에서 ±20°(K0은 ±5°)까지만 돌아간다.
- 치마는 사슬 세 개(각 세 마디)에 물리가 걸린 메시다.

## 방법: 단위별로 비교한다

영상과 리그를 **한 번에 하나의 단위씩** 비교한다.

| 단위 | 영상과 비교할 것 |
| --- | --- |
| 머리 | 표정, 눈 깜빡임, 머리 기울기 |
| 팔 | 팔 각도, 관절 각도, 손모양, 손이 몸의 **앞인지 뒤인지** |
| 몸 | 숨쉬기, 들썩임 · 점프, 몸통 흔들림 |
| 다리 | 발이 바닥에 안정적으로 붙어 있는지, 무언가 다리를 뚫고 지나가지 않는지 |
| 옷 | 치마의 흔들림 · 퍼짐 · 주름 변형 |

발견한 것은 하나하나 아래 넷 중 하나로 분류한다.

- **리그 고침**: 그리는 순서, 조각, 물리 값 등
- **모션 고침**: 키, 타이밍, 교체 시점
- **새 그림 필요**: 새 세트, 또는 기존 세트를 다른 각도로
- **도구가 했어야 함**: 입력만 보고 자동으로 할 수 있었던 것

## 입력 (`inputs/`)

| 경로 | 내용 |
| --- | --- |
| `reference/ref1080.mp4` | 레퍼런스 춤 영상(1080×1920, 24 fps, 313프레임, 13초). **이 폴더 밖으로 내보내지 말 것** |
| `reference/audio.mp3` | 그 영상의 음악(0초 시작) |
| `reference/pose.json` | 영상에서 뽑은 관절 좌표(프레임별 body-17 + neck, `rig-c-pose-frames/0`) |
| `rig/` | 리그 스펙(`rig.json`, `motion.json` 등)과 조각 이미지. 세트 K0~K4 포함 |
| `dance/build/` | 춤을 입혀 빌드한 결과(스파인 4.3 데이터 + `skeleton.model.json`) |
| `dance/motion.json` | 리타깃된 춤 모션 |
| `dance/map.json` | 관절 지도와 세트 정의(`alternates`) |
| `dance/report.json`, `dance/run.txt` | 리타깃 리포트(교체 구간, 범위 초과, 접힘 등) |
| `dance/clip-audio.mp4` | 현재 상태 데모: 왼쪽 영상, 오른쪽 리그, 음악 포함 |
| `sets/` | 원본 그림과 세트 그림 다섯 장(세트가 어떤 그림에서 왔는지 보는 용도) |

## 도구

`package.json`에 버전을 고정해 두었다. 이 폴더에서 `npm install` 또는 `bun install`을 실행한다. 필요하면 Bun 1.2 이상.

- `rigc`(rig-c 2.51.1): `build`, `render`(프레임 · `--geometry` · `--folds`), `inspect`, `guide`. 각 패키지의 README와 `docs/AUTHORING.md`가 정본이다. 실패 줄 끝의 `(see rigc guide …)`를 따라가면 된다.
- `rig-pose`(@rig-c/pose 0.6.0): `retarget`(지도 · 세트 · 범위 · `--smooth` · `--flip` · `--short`)
- `rig-parts`(@rig-c/parts 1.17.0): 참고용

**모델 이름:** 응시를 시작한 사람이 프롬프트에 적어 준 이름을 그대로 쓴다. 스스로 짐작하지 않는다(모델은 자기 이름을 자주 틀린다). `run/report.md` 맨 위와 `run/journal.md` 제목에 그 이름을 쓴다.

## 작업 폴더

모든 결과는 이 폴더 안의 `run/`에 둔다.

| 파일 | 내용 |
| --- | --- |
| `run/journal.md` | 일지. `JOURNAL.md`를 복사해서 쓴다(아래 규칙) |
| `run/transcript.md` | 실행한 명령 기록 |
| `run/findings.md` | 찾은 것 |
| `run/evidence/` | 증거 이미지 |
| `run/after/` | 고친 리그 · 빌드 · 데모 |
| `run/report.md` | 보고 |
| `run/tools.md` | 도구가 아쉬웠던 점 |
| `run/usage.json` | 토큰(알 수 있을 때만, 부대 몫 포함) |

## 해야 할 것

1. **찾기**: 단위별로 영상과 리그를 비교해서 `run/findings.md`를 쓴다. 발견마다 다음을 적는다.
   - 단위
   - 시간(초)과 프레임 범위
   - 무엇이 틀렸는지
   - 증거 이미지: `run/evidence/` 아래에 영상 | 리그를 나란히 놓은 프레임
   - 분류(위 넷 중 하나)
   - 심각도(높음 · 중간 · 낮음)
2. **고치기**: 심각도가 높은 것부터, 이 폴더 안에서 고칠 수 있는 것을 고친다. 리그 스펙, 모션, 지도, 물리 값 등을 고칠 수 있다. 고친 것은 다시 빌드한다(`rigc` 게이트 초록). 다시 렌더해서 `run/after/clip-audio.mp4`를 만든다. 형식은 `inputs/dance/clip-audio.mp4`와 같다(왼쪽 영상, 오른쪽 리그, 음악 0초 맞춤).
3. **보고**: `run/report.md`에 다음을 쓴다.
   - 발견 목록 요약
   - 고친 것과 전후 비교(이미지 · 수치)
   - 못 고친 것과 그 이유. 새 그림이 필요하면 어떤 자세 · 각도를 그려야 하는지
   - 도구가 했어야 할 것의 목록

## 일지 · 기록 규칙 (가장 중요)

- **행동 전에 일지를 쓴다.** 무언가를 바꾸는 단계(파일을 쓰거나, 빌드 · 렌더하는 명령)마다 `run/journal.md`에 항목을 하나 쓴다. 1~3행(읽은 것, 예상, 고른 것 · 버린 것)은 **단계 전에**, 4행(일어난 것)은 **단계 후에** 쓴다. 결과가 예상과 다르면 4행을 `WTF?:`로 시작하고, 와닿은 그대로 쓴다. 사후에 쓴 항목은 가치가 없다. 단계 전에 써 둔 틀린 예상이 이 파일에서 가장 쓸모 있는 줄이다. **통과보다 이게 더 중요하다.**
- **transcript**: 무언가를 바꾸거나 빌드한 모든 명령을 순서대로, 출력의 마지막 몇 줄과 함께 `run/transcript.md`에 남긴다.
- **시간**: 시작 전에 `date -u +%Y-%m-%dT%H:%M:%SZ`를 실행해서 그 출력을 `run/transcript.md`의 첫 줄 `started: <출력>`으로 쓴다. 마지막 렌더가 끝난 뒤 다시 실행해서 마지막 줄 `finished: <출력>`으로 쓴다. 어림하지 않는다.
- **토큰**: 실행 환경이 세션 사용량을 알려 주면 `run/usage.json`에 `{"input_fresh": n, "input_cached": n, "output": n}`(또는 `{"total": n}`)과 출처를 쓴다. 알 수 없으면 파일을 만들지 않는다. 어림하지 않는다.
- **막히면 멈춘다**: 더 갈 수 없으면 마지막 항목(시도한 것, 행동으로 옮길 수 없었던 메시지)을 쓰고 보고로 넘어간다. 결과를 지어내지 않는다.

## 마지막: 도구가 아쉬웠던 점

끝나면, 넘기기 전에 `run/tools.md`를 쓴다. 이 문제가 아니라 **세 패키지**에 대해 아쉬웠던 것을, 하나당 한 항목으로, 있었던 만큼:

    ## <짧은 제목>
    - **하려던 것:** 무엇을 하려 했는지, 자기 말로
    - **도구가 준 것:** 가지고 있던 메시지 · 파일 · 절. 인용한다
    - **있었으면 했던 것:** 바랐던 문장 · 메시지 · 옵션 · 명령
    - **비용:** 대략 얼마나 걸렸고, 결국 해냈는지

일지와 transcript에 실제로 부딪힌 것만 쓴다. 부풀리지 말고, 필요 없었던 건 쓰지 않는다. 정확한 줄을 짚은 항목이 막연한 바람보다 낫다.

## 끝나면 답할 것

1. 찾은 것: 단위별 개수와 심각도 높은 것 목록
2. 고친 것: 무엇을 어떻게 고쳤고, 어디(문서 절 · 메시지)에서 방법을 찾았는지
3. 단위별 일지 항목 수와, 4행이 `WTF?:`로 시작하는 항목 수. 부대를 몇 번 띄웠고 각각 무엇을 맡겼는지
4. 시간을 가장 많이 쓴 세 가지와, 관련 문서 절이나 메시지
5. `tools.md` 항목 제목들

## 규칙

- 이 폴더(`<problem folder>/`) 안에서만 읽고 쓴다. 다른 폴더나 다른 레포는 보지 않는다. 예외는 `npm install`로 이 폴더의 `node_modules/`에 설치된 세 패키지(`README.md` · `docs/` · `--help`)와 그 공개 페이지(github.com/rig-c/core · parts · pose)뿐이다. 사람에게 도움을 청하지 않는다.
- **커밋 · 푸시 없이 로컬에서만 작업한다.** git 명령(add · commit · push 포함)은 일절 쓰지 않는다. 결과물은 이 폴더에 파일로만 남긴다.
- **부대를 써도 된다. 부대를 부리는 것도 능력이다.** 하위 에이전트를 몇이든 띄워도 된다. 다만 띄울 때마다 일지에 항목을 하나 쓴다. 1~3행(맡긴 일, 기대한 결과물, 그 모델 · 개수를 고른 이유)은 띄우기 전에, 4행(돌아온 것, 받아들였는지 · 고쳤는지)은 돌아온 뒤에 쓴다. 부대의 모델 이름과 맡긴 범위는 `run/report.md`에도 모아 적는다. 결과에 이름이 오르는 건 지휘한 모델이고, 부대의 결과물을 받아들인 판단도 그 모델의 몫이다.
- 이 문제 밖의 세션 · 에이전트와 교신(브릿지 포함)하지 않는다. 이 맥에서만 돌리고, 원격 GPU나 원격 실행(노바 등)은 쓰지 않는다. 사람에게 도움을 청하지 않는다.
- 레퍼런스 영상과 그 프레임이 들어간 이미지 · 영상은 이 폴더 밖으로 내보내거나 어디에도 올리지 않는다.
- 빌드 · 렌더는 1분 넘게 걸릴 수 있다. 끝날 때까지 기다린 뒤 결과를 읽는다.
